## 交接顺序

1. A 核验客流，B 整理两地日历，两项并行。
2. B 将日历交给 A。A 交付合表结果、清洗脚本和字段说明，C 抽查复核后交给组长。
3. 组长完成分析和两个模型，把图表、评估结果、优化效果对比和预测结果交给 B 与 C。B 开始实现原型，组长同步撰写报告，C 准备课堂汇报。
4. B 完成联调并交付可运行的原型与演示步骤。组长补齐原型应用部分并定稿报告，A 录制项目视频，C 完成 PPT 并准备现场演示。待材料齐备后，A 整理提交包。

## GitHub 协作

一条 Issue 跟进一项可验收的任务。分工表记录长期职责，Issue 记录这次要交什么、目前进展和遇到的问题。

1. **组长建单并指派。** 打开仓库的 [Issues 页面](https://github.com/lzndXJ/Statistical_Analysis_and_Modeling_Final_Project/issues)，点 `New issue`，填入标题、交付物和验收清单。发出后在右栏 `Assignees` 选择认领这项工作的队友。若找不到队友，先确认对方已接受仓库邀请。 [创建 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue) · [指派 Issue](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/assigning-issues-and-pull-requests-to-other-github-users)
2. **负责人用同一条 Issue 更新进展。** 开始后留言说明已开始。完成一个检查项就勾选相应复选框。需要等其他任务时，留言写明还缺什么，并用 `#编号` 链接相关 Issue。打开 Issue 就能看到谁负责、做到哪一步以及下一步等什么。
3. **负责人提交 PR。** 在个人分支提交成果后，向仓库默认分支发起 PR，在描述里说明改动、交付文件和验证结果。如果这次 PR 完成了整条 Issue，在描述里写 `Closes #实际编号`，例如 `Closes #3`。如果只交了一部分，写 `Refs #3` 并留言说明还有什么要完成。 [将 PR 与 Issue 关联](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)
4. **组长验收并合并。** 对照 Issue 的清单审阅 PR，有问题就在 PR 里提出。完成任务且 PR 合并进默认分支后，带 `Closes` 的 Issue 会自动关闭。只交了一部分的 Issue 继续保持打开。
